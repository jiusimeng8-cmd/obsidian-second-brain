# 适配其他 AI 客户端

本项目不绑定 OpenCode。OpenCode / OpenChamber 只是**已经写好的参考适配器**（`second-brain/api.py`）。
Codex CLI、Claude Code、ZCode、Cursor、自建 Agent 平台……只要能满足下面的能力契约，就能接进来。

## 能力契约（四个动作）

适配器只需要实现四件事，其余全部复用：采集、选择、台账、核验、看板、预算、轮换都不依赖具体客户端。

| # | 能力 | 必须返回什么 | 为什么必须 |
| --- | --- | --- | --- |
| 1 | **列会话** | `id`、`title`、`directory/项目`、`archived`、`updated` | 盘点全量历史，归档也要算 |
| 2 | **读消息（完整历史）** | 按时间升序；每条含 `id`、`kind`(user/assistant/tool)、`created`、正文、是否已结束（`idle` 或 `finish`/`completed`）；能分页 | 读取增量、冻结已结束回合、抽取证据、标注来源消息 ID |
| 3 | **派发任务** | 能复用/新建一个会话、指定模型、投递一段文本，并能判断**它已经跑完** | 单一可见整理会话 + 串行执行 + 完成判定 |
| 4 | **读写笔记** | 任意 MCP 或本地文件接口，能按路径读、按路径写、**写完能读回** | 核验要求真实回读，不接受「模型说写了」 |

如果第 3 项做不到「能判断跑完」，就必须至少做到「能读到该会话的最后一条消息」——
否则无法核验，只能退化成人工触发。

## OpenCode / OpenChamber（参考实现）

见 `second-brain/api.py`。要点：

- 端口与本地令牌在 `~/.config/openchamber/settings.json`（`desktopLocalPort`、`desktopLocalClientToken`），只读不打印。
- 会话列表/消息：`GET /api/session`、`GET /api/session/{id}/message`，游标分页。
- 派发：`POST /api/session/{id}/prompt`（`delivery:"queue"`，自带 `id` 便于对账）。
- 完成：会话 `time.idle`，或消息的 `time.completed` + `finish`。
- 模型：`GET /api/model`；`POST /api/session/{id}/model` 的 `model.id` 必须是裸模型 ID。

## Codex CLI

- 会话：`~/.codex/sessions/**/rollout-*.jsonl`（JSONL，逐行事件），或官方 `codex exec` / SDK 的会话列表接口。
- 派发：`codex exec --json "<提示词>"`（无头），或 SDK 的会话创建 + 发送。
- 完成判定：进程退出码 + 最后一条 assistant 消息存在 `finish`/结束事件；**不要**只看文件是否停止增长。
- 工具轨迹：rollout 里通常保留工具调用事件；若被裁剪，见下面「证据变弱的处理」。

## Claude Code

- 会话：`~/.claude/projects/<项目 slug>/*.jsonl`，每行一条消息/事件。
- 派发：`claude -p "<提示词>" --output-format json`（无头），或 SDK。
- 完成判定：命令结束 + 结果 JSON 里的停止原因。
- 注意：子代理（Task）会话是独立文件，属于同一条主线的延续，按 fork 处理（共享前缀去重，新结论照常处理）。

## 纯文件型 / 其他平台

很多客户端只留下本地记录，没有 API。此时适配器是**只读快照 + 外部触发**：

1. 定时扫描记录目录，按 `session id + 事件时间` 排序。
2. 用「最后一条消息有结束标记 + 文件 mtime 静默 ≥ `quiet_seconds`」判定回合结束——
   两个条件都要，只靠 mtime 会在长任务中途切段。
3. 派发改为：调用该平台的 CLI/HTTP（若有），或用你自己的另一个 Agent 执行同一条提示词。
4. 完全无法派发时，仍可只做「采集 + 生成任务包」，由你手动喂给任意模型；核验逻辑不变。

## 移植时要改的地方

| 层 | 是否要改 | 说明 |
| --- | --- | --- |
| `api.py` | **要改** | 换成目标客户端的四个动作，返回同样的数据结构 |
| `collector.py` | 小改 | 消息字段名不同时加一层归一化；采样策略、冻结规则、游标逻辑不变 |
| `focus.py` | 不改 | 只吃归一化后的消息 |
| `quality.py` | 可能小改 | 取决于工具轨迹的格式 |
| `worker.py` | 小改 | 会话创建/模型切换/完成判定换成目标客户端 |
| `storage.py` | 不改 | 台账 schema 已与客户端无关 |
| 插件 | 要改 | OpenCode 用 V2 插件守护进程；其他平台用 systemd / launchd / 计划任务 |

建议做法：保留 `api.py` 的**返回结构**（`sessions()` / `messages()` / `prompt()` / `update()`），
只替换内部实现。这样上层一行不用动，测试也能直接复用。

## 证据变弱的处理（重要）

有的客户端记录里没有工具调用，只有对话文本。这会让核验从「读/写轨迹 + 文件哈希 + 引文 + 来源」退化为
「文件哈希变化 + 引文 + 来源会话/消息 ID」。

此时必须：

1. 在台账里把该任务的证据等级降一级（例如 `written_verified_weak`），不要和强证据混为一谈。
2. 看板分开统计，避免「通过率」看着很好但其实是弱证据。
3. 提示词里明确要求模型输出实际写入路径与逐字引文——弱证据下，这两个是唯一可核对的部分。

不要为了「看起来一致」而伪造工具轨迹，也不要把弱证据当成强证据。

## 一个客户端够不够

多客户端并存时，建议：

- **一个客户端一个适配器，共用一套台账**，用 `sources.id` 前缀区分来源（如 `codex:`、`cc:`、`oc:`）。
- 笔记库只有一座，写者会话也只有**一个**——跨客户端再并行写，冲突只会更多。
- 各客户端的工具能力不同：写者会话最好放在工具最全的那个客户端里。
