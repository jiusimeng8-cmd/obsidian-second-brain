# 架构

## 为什么不是「一个插件搞定」

第一版确实是纯插件：在 `session.idle` 时新建一个子会话去总结。三个问题很快暴露：

1. **列表污染。** 每次整理都是一个新会话，几十上百个「[Obsidian memory]」堆在侧栏。
2. **状态只在内存。** 插件热重载或进程重启，队列就没了；失败无法重试。
3. **没有核验。** 模型说「已写入」，实际工具调用失败了，没人知道。

现在的形态是：**插件只做守护，逻辑全在独立进程，状态全在独立数据库。**

```
plugin/obsidian-memory.js       每 60s 看一次心跳，超过 90s 就拉起 worker
        │ spawn（detached，隐藏窗口，无 stdio）
        ▼
second-brain/worker.py          OS 文件锁 → 只有一个实例真正消费
        ├─ collector.py   采集
        ├─ focus.py       选择与批次
        ├─ quality.py     核验
        ├─ api.py         本机 HTTP API
        └─ storage.py     SQLite 台账
```

后台进程没有任何监听端口，因此不需要开防火墙、也不占端口。存活以「心跳文件 + 进程命令行」为准。

## 数据流

```
1. 盘点 inventory
   GET /api/session?archived=false|true，分页取全
   → sources 表（含父子关系、目录、更新时间、是否归档）

2. 采集 capture
   对每个有变化的来源：
     focus 模式：开头 30 条 + 最新 200 条（缺口显式标记为未精读）
     完整模式：游标之后全部分页
   冻结到「最后一个已结束回合」（idle，或旧记录里已完成且 finish=stop 的 assistant）
   静默 >= quiet_seconds 才冻结，避免打断正在进行的对话
   长消息无损切分为 #partN/total，原文全部落库
   → messages 表 + sources.captured_id

3. 选择 select（focus.py）
   每个来源取有界窗口：
     锚点：首条用户消息 + 最近 3 条有意义的正文
     其次：中间明确的决定 / 偏好 / 纠正 / 结论
     排除：工具输出、代码块、超长日志行、寒暄
     每条最多 1100 字符，超出留省略标记
   相关来源合并为一批（默认每源 6000 字符、最多 12 源、合计 48000 字符）
   → jobs 表（focus_ 前缀）+ focus_ranges 表（选择覆盖范围）

4. 派发 dispatch
   串行：一次只有一个 processing
   恢复优先：上次中断的 processing 任务先完成核验，再开新任务
   预算：滚动 24 小时提交次数（含重试）<= daily_job_limit
   选择：待处理 / 失败未超次数且到重试时间；同来源更早的失败会阻塞后面的范围
   写者：确保只有一个可见整理会话；超长则归档并新建（带 previous 交接）
   模型：从运行中的模型目录现场挑选，DeepSeek Flash 族优先，失败进冷却
   → 固定 message_id 投递（可在崩溃后精确找回）

5. 整理 steward
   目标会话收到一段任务提示词 + 证据窗口，只能做笔记维护
   允许：读规则、按对象/别名检索、合并时间线、写/改笔记、回读
   必须：为事实标注来源会话与消息 ID、记录时间、区分「用户说的/工具证实的/助手推断」
   输出单行 BRAIN_RECEIPT（状态 + 原因 + 覆盖的消息引用 + 笔记路径与逐字引文）

6. 核验 verify
   任务 ID 必须对得上；覆盖引用必须完整
   written：文件确实变过 + 存在完成的写入工具调用 + 存在完成的回读 + 引文逐字存在 + 来源 ID 在文中
   duplicate：存在完成的回读 + 引文存在（并指向带来源的主笔记）
   no_value：只允许寒暄/确认类内容，且有具体原因
   通过 → written_verified / skipped_verified / focus_screened
   不通过 → failed，保留任务与证据，按退避重试

7. 对外可见
   state/health.json         机器可读心跳与计数
   <vault>/01-看板/第二大脑处理进度.md   人读看板：窗口数、选取/原始字符、批次状态、预算、最近结果
```

## 状态机

任务状态：

```
pending ──dispatch──> processing ──verify ok──> written_verified
                            │                └> skipped_verified   （内容已存在）
                            │                └> focus_screened     （窗口内无可提取信息，非完整审阅）
                            └──verify fail / timeout──> failed ──retry──> pending
pending ──被重点窗口接管──> superseded（证据保留，不再计入必做）
任意 ──来源被排除──> excluded
```

来源游标有两套，故意分开：

| 游标 | 含义 | 推进条件 |
| --- | --- | --- |
| `sources.captured_id` | 这段消息已经落库 | 采集完成并冻结 |
| `sources.acknowledged_id` | 这段消息已进入笔记或被明确判定无需记录 | 只有**连续**的已核验任务才推进 |
| `focus_ranges.last_position` | 这段范围已被重点窗口选择过 | 生成批次即记录（含未选中的说明） |

## 数据表

| 表 | 作用 |
| --- | --- |
| `meta` | 键值：写者会话、上一位写者、提交时间戳、MCP 服务标识、目录轮转 |
| `sources` | 每个会话：目录、标题、归档、游标、扫描时间、状态、错误、原始信息 |
| `messages` | 采集到的消息：位置、时间、类型、指纹、正文（已脱敏、无损分段） |
| `jobs` | 任务：证据、引用清单、状态、次数、时间、写者、提示 ID、模型、回执、错误 |
| `verified_messages` | 已核验的消息指纹，用于 fork 共享历史的去重 |
| `models` | 模型冷却、成功/失败计数 |
| `focus_ranges` | 每个批次对每个来源选择的范围与字符量（选择覆盖，不是事实确认） |

`messages` 与 `jobs` 只增不删；`superseded` 也是保留状态，不是删除。

## 模型选择

不写死模型名，运行时从 `/api/model` 读取当前真实可用目录，按序：

1. 台账里记住且仍在目录中的模型
2. 显式配置（如需要）
3. `preferred_family` 正则（默认 `deepseek.*flash`）
4. 小模型关键词（flash / mini / nano / lite / haiku / turbo / air）
5. `preferred_providers` 顺序
6. 同族版本号倒序
7. 过滤：不可用、无工具能力、已弃用、`-free`（桌面端会拒绝）

模型或供应商层面的错误（401/429/无路由）触发冷却，工具类失败不牵连模型。
「目录里存在」只代表已注册，不代表已验证可用；真实可用性由任务结果证明。

## 为什么核验要这么严

整理者最常见、也最难发现的失败不是报错，而是**流畅地说自己做了什么**。
所以「完成」的判定不读它的自述，只读三类独立证据：

1. 文件系统：前后哈希不同、路径在库内、不在凭据/隐藏目录
2. 工具轨迹：`state.status == completed` 的真实 `write_note` / `patch_note` / `read_note` 调用
3. 内容与来源：引文逐字存在、来源会话与消息 ID 出现在正文

三者缺一即失败。这挡不住「事实本身有误」，但能挡住「没写却说写了」。

## 已知边界

- 首轮抽样只读开头与最新部分，中间细节需靠原文回查；台账里记录了缺口。
- 助手断言一律标记为「需核实」，不会被当成事实；核验只保证来源可追。
- 附件只保留文件名与类型。
- 与 Codex / 其他客户端无集成。
- 每日预算是硬约束，全量历史回补是长期后台任务。
